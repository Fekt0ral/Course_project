# Автоматизированная система оценки рисков кредитного портфеля банка

## Куратор - Александр Голубев

## Цель проекта

Разработать и развернуть сервис скоринга клиентов, который по заявке на кредит возвращает вероятность дефолта заёмщика. Сервис будет включать REST API, форму для ввода заявки и дашборд для аналитиков с распределением рисков и динамикой портфеля.

Исследовательская часть будет сравнивать классические модели с DL-подходами для табличных и текстовых данных и отвечать на вопрос, оправдывает ли DL своё усложнение в задаче кредитного скоринга.

## Данные

### Табличная часть: LendingClub (2007–2018)

- **Источник:** [All Lending Club loan data](https://www.kaggle.com/datasets/wordsforthewise/lending-club) (Kaggle, лицензия CC0).
- **Почему он:**
  - реальные займы, более 2 млн записей;
  - финансовые признаки и кредитная история заёмщика;
  - есть дата выдачи займа, поэтому возможно разбиение по времени и моделирование дрейфа.
- **Таргет:**
  - `Charged Off` = дефолт (1);
  - `Fully Paid` = не дефолт (0);
  - займы в промежуточных статусах (`Current`, `Late`, `In Grace Period` и др.) исключаются.
- **Отбор признаков:** используются только признаки, известные в момент подачи заявки. Поля, отражающие историю погашения (выплаченные суммы, даты последних платежей и т.п.), удаляются, чтобы избежать утечки целевой переменной.

### Текстовая часть: синтетические комментарии к заявкам

В открытых кредитных датасетах нет текстовых полей. Поэтому текстовые признаки (описание цели кредита, комментарий к заявке) будут генерироваться с помощью LLM.

**Принцип генерации:** текст строится только по признакам заявки (доход, цель кредита, стаж, сумма и т. д.), без информации об исходе займа. Это исключает утечку таргета через текст. Если бы генератор знал, вернул ли клиент кредит, он мог бы оставить в тексте подсказки, и модели показали бы завышенное качество.

**Проверка:** модель, обученная только на тексте, не должна заметно превосходить модель на табличных признаках. Если превосходит, генератор «подсказывает» ответ и требует доработки.

## Исследовательские вопросы

1. Насколько сильна хорошо настроенная классическая модель (CatBoost) на табличных кредитных данных?
2. Какой способ работы с дисбалансом классов лучше для данной задачи: взвешивание классов, undersampling или SMOTE? Как каждый из них влияет на калибровку вероятностей?
3. Дают ли DL-модели для таблиц (TabTransformer, DeepFM) прирост относительно градиентного бустинга?
4. Несут ли текстовые признаки (эмбеддинги BERT-подобных моделей) дополнительную информацию сверх табличных?
5. Какая модель оптимальна для продакшена с учётом качества, калибровки, скорости и сложности поддержки?

## Метрики

| Метрика | Зачем |
|---|---|
| ROC-AUC | Общее качество ранжирования клиентов по риску |
| PR-AUC | Качество на миноритарном классе (дефолты) при дисбалансе |
| F1 на классе дефолтов | Качество бинарного решения при выбранном пороге |
| Brier score, график калибровки | Насколько выдаваемым вероятностям можно доверять, а не только ранжированию |

**Валидация:** разбиение по времени. Модель обучается на ранних годах, а валидируется и тестируется на более поздних. Это соответствует реальному применению модели к будущим заявкам.

## Возможные расширения

Реализуются при наличии времени после выполнения основного объёма:

- **Мониторинг дрейфа:** PSI по ключевым признакам и по скору модели, алерты при деградации качества.
- **Объяснимость:** SHAP-значения в ответе API, чтобы было видно, какие факторы повлияли на оценку риска.
- **Экономический порог:** выбор порога одобрения через функцию потерь банка вместо F1.
- **Fairness:** анализ непредвзятости модели по защищённым признакам (в пределах того, что доступно в данных).

| Исчезновение датасета из открытого доступа | Локальная копия исходных данных, зафиксированный источник |
